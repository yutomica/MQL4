# EAコーディング規約

採用方針の文書化日：2026-10-11

2026-10-11改訂：ユーザーの簡素化指示により、TradeControlの責務を排他・送信間隔・待たずに戻る制御へ限定する。初版の要求管理・永続保存・自動復旧を共通モジュールへ組み込む方針は廃止する。

## 1. 目的と適用範囲

本規約は、MQL4リポジトリで新規作成するEAと、依頼範囲に含まれる既存EAの改修に適用する。異なる通貨ペア・時間足のEAを同一MT4ターミナル・同一口座で同時運用でき、個別バックテストと実運用で同じEAを使用できる構成を基本とする。

正本は、本リポジトリの `docs/EA_CODING_STANDARD.md` とする。EABuilderなどの別プロジェクトへ規約本文のコピーを作らず、同じ正本を参照する。外部プロジェクトの場所は、EABuilderの `PROJECT_MAP.md` に従う。

ユーザーの明示的な依頼と、適用される `AGENTS.md` の作業規則に従う。本規約は、既存の編集範囲・コンパイル・実運用への導入に関する規則を変更しない。既存EAを規約へ合わせるための一括改修を、依頼に含まれない作業へ追加しない。

既存EAへの共通注文制御の導入は、依頼された移行範囲で行う。局所修正だけの依頼に、全面移行を追加しない。以下の共通注文制御に関する必須規則は、本構成で新規作成するEAと、共通注文制御への移行を行うEAに適用する。

過去の案A・案Bの説明資料は検討記録であり、標準構成は以下の採用方針とする。

## 2. 標準のファイル構成

1つの戦略を1つのEAとして実装し、戦略固有のロジックと状態管理は各 `.mq4` に置く。注文制御は `Include/Original/TradeControl.mqh` に集約する。

```text
Experts/
  STR01_USDJPY_H1.mq4
  STR02_USDJPY_H1.mq4
  STR03_USDJPY_M30.mq4
  ...追加する各戦略EA...

Include/Original/
  TradeControl.mqh
```

- 各EAは `#include <Original/TradeControl.mqh>` を使用する。
- `StrategyRunner.mqh`、戦略ごとの `.mqh`、専用の `TradeExecutor.mq4` は標準構成に含めない。
- 共通化だけを目的にクラス階層や汎用フレームワークを追加しない。既存の単純な関数・変数で明確に表現できる場合は、その形を使う。
- 補助関数の追加は適用される `AGENTS.md` に従い、依頼内容に必要な範囲とする。
- 具体的な再利用目的や依頼上の必要性が生じた場合に、追加のファイル分割を検討する。既存のリスク計算・指標などの共有部品を、この構成に合わせるだけの目的で削除・統合しない。

具体的なAPIは実装された `TradeControl.mqh` を正本とする。既存EAへの組込みや実稼働の検証完了は、共通モジュールの作成・コンパイル成功とは区別する。

## 3. 各EAと共通モジュールの責務

| 各戦略EAのmq4に置くもの | TradeControl.mqhに置くもの |
|---|---|
| 入力設定・銘柄・時間足・Magic、売買判断 | EA間の注文送信の排他制御 |
| 注文価格・数量・SL等の決定と直前確認 | 参加EA共通の送信間隔の制御 |
| 要求の保持・期限・再試行の判断 | 送信できない場合に待たずに戻る処理 |
| 注文APIの呼出し、戻り値・エラーの取得 | 上記に必要なテスト／実運用の状態・時計の切替 |
| OCO・部分決済・日次売買などの戦略状態 | — |
| 必要な状態保存、結果不明時の照合、復旧 | — |

EAは「何を、どの条件で売買するか」と結果を管理し、共通モジュールは「今、注文APIを呼んでよいか」だけを制御する。要求キュー・要求ID・参加番号・履歴照合・自動再試行・永続ジャーナル・公平な順番管理はTradeControlに追加しない。

同じmqhをincludeしても、通常の変数の実体はEAごとに別である。EA間で共有する実行権・送信間隔には、ターミナルのグローバル変数など、明示的な共有手段を使用する。各EAの注文要求を一か所へ配送する専用Executorや、EA間の再検証依頼・結果通知を前提にしない。

## 4. EAから注文処理を呼ぶ際の規則

- `OnInit`で `TC_Init(interval_ms)` を呼ぶ。参加EAはすべて同じ送信間隔を使う。設定一致は実運用の `TC_Begin()` で確認する。間隔変更時は全EAの設定を揃えてターミナルを再起動する。
- 新規、決済、変更、取消などの注文APIは、各EAの `TC_Begin()` がtrueを返した後、`TC_End()` までの間に1回だけ呼ぶ。既存共有部品にも制御を迂回する経路を残さない。
- `TC_Begin()` がfalseなら注文は呼ばれていない。待機を注文成功・注文失敗・エラー141として扱わず、必要な要求をEA側で保持して後続イベントへ戻る。
- 実行権を取得してから、銘柄・Magic・対象注文・気配・ロット・価格制約・戦略条件を再確認する。見送る場合は `TC_End(false)` を呼んでから戻る。
- 注文APIの戻り値と `GetLastError()` は `TC_End()` より先に取得する。APIを呼んだ場合は成否にかかわらず `TC_End(true)` を呼ぶ。Endの成否と注文の成否を混同しない。
- BeginからEndまでは同一イベント内で完結させ、Sleep・長い処理・解放を忘れたreturnを挟まない。
- 順番待ちを理由に、元の価格・数量・シグナル・有効期限を無条件に再計算・延長しない。変更が必要な場合は、その戦略の明示的な規則に従う。
- 結果の反映、保留状態の解消、必要な永続化は各EAで実装する。必要のない汎用要求管理の仕組みを全EAへ強制しない。
- タイムアウト・異常終了等の結果不明では、各EAが実注文・履歴と照合する。TradeControlは二重注文を自動検出しない。確認できないまま新規注文や部分決済を再送せず、待機注文の設置成功とその後の約定も区別する。

関数名・引数・戻り値の具体的な定義は、実装された `TradeControl.mqh` をAPIの正本とする。変更時にはすべての利用EAとの整合を確認する。本規約中の責務名を、実装済み関数名と解釈してはいけない。

## 5. 共通注文制御の必須動作

### 5.1 実行権と送信間隔

制御範囲は、同一ターミナル・同一サーバー・同一口座の参加EA全体とする。銘柄・時間足・Magicごとに発注枠を分けない。別ターミナル、手動注文、共通制御を使用しないEAまで自動的に統制できるとは扱わない。

1. 空の共通ファイルを排他的に開き、実行権を1つのEAだけが取得する。ファイルへ注文情報を書き込まない。
2. 取得後に端末の一時グローバル変数から送信間隔・前回完了時刻を読む。間隔未満なら実行権を返してfalseを返す。
3. EAが条件を再検証し、注文APIを1回呼び、戻り値とエラーを取得する。
4. `TC_End(true)` が前回完了時刻を更新してから実行権を解放する。未送信の `TC_End(false)` は時刻を更新せず解放する。
5. 共通時刻更新に失敗した場合はfalseを返して実行権を保持する。EAは注文結果と制御エラーを別に処理する。`TC_End(true)` 失敗後に `TC_End(false)` で解放せず、時刻更新の再試行には `TC_End(true)` を使う。

`IsTradeContextBusy()`などの事前確認だけを排他制御の代用にしない。共有状態を初期化する際に、他EAの実行権や前回完了時刻を上書きしない。利用EAは同じ共通モジュールを使い、送信間隔の設定不一致を検出する。

### 5.2 待機と機能の限界

- 実行権の取得待ちや送信間隔の待機で、`Sleep()`や待機ループを使用しない。要求を保持してイベント処理を終える。
- 実行権は取得できたEAへ渡す。公平な順番や各EAの最大待ち時間は保証しない。API実行中の所有者から時間切れで実行権を奪う処理も追加しない。
- TradeControlは要求や結果を永続保存せず、異常終了・再起動からの自動復旧を行わない。必要な状態の保持と実注文の照合は各EAの責務とする。
- 送信間隔に根拠のない固定値を安全値として埋め込まない。約8本の同時運用を想定しても、全要求を数秒以内に処理できるとは保証しない。

この方式では、注文APIの応答待ちの間、発注したEA自身のイベント処理は待たされる。専用Executor方式と同じ非同期動作を実現したと説明しない。

## 6. 新バー・時間足・戦略状態

- 新バーを評価済みにした状態と、注文要求が完了した状態を分ける。保存済み要求は次のバーまで放置せず、後続イベントで継続する。同じバーを毎回再評価して重複要求を作らない。
- 価格系列・指標は意図した銘柄と時間足を参照する。高安の位置を求める処理と、その位置の価格を読む処理でも参照先を一致させる。
- OCOは両脚を関連付け、片脚の送信・約定・取消と、次の操作の依存関係を管理する。OCOの2注文をサーバー上の不可分な処理とは扱わない。
- 部分決済は基準数量・確認済み決済数量・残数量を追跡し、結果不明や結果再反映で二重決済しない。
- 日次の発注予約はEA内で同じ要求と識別できるように管理する。同じ要求の再検証で自分の予約を理由に拒否せず、未送信と確定した取消と結果不明の場合で解除条件を分ける。
- 既存EAの起動直後のバー評価、指標シフト、取引時刻の変換、価格・数量の再検証方針は維持する。構成変更に便乗して売買条件を変更しない。

## 7. 個別バックテストと実運用

- 移行後の同じ `.mq4` とコンパイル済みEAを、個別バックテストと実運用の両方に使用できる構成にする。戦略をコピーしたテスト専用版・本番専用版を二重保守しない。
- 共通注文処理内で `IsTesting()`等を使い、テスト中はそのEA専用の制御状態、実運用ではターミナル共有の制御状態を使用する。デモ口座上のチャート稼働も実運用側の共有制御に含める。
- テスト中もBegin/Endで同じ送信間隔を判定し、制御全体を迂回しない。EA側の要求保持・再検証・期限・再試行・結果反映も同じ経路を使う。
- バックテストの待ち時間はテスターの時刻で判定する。実運用の送信間隔には実際の経過時間を用い、売買条件で使うサーバー時刻・JST等と混同しない。
- テスト用の要求・保存状態・共有変数は実運用と分離し、各テストで意図した初期状態に戻す。過去のテストや実運用の保留要求を読み込まない。
- 既存EAにあるテスト／実運用の初期化上の違いは、移行時に明示して維持する。共通化を理由に無断で統一しない。
- MT4テスターではTimer・ChartEventが処理されないため、必要な注文処理を `OnTick()`から進められるようにする。実運用のタイマーは既存要求の継続に使用し、新しいシグナル評価の機会を無断で増やさない。
- 単独EAのバックテストを、ほかのEAの順番待ち・口座全体の証拠金使用・実通信遅延・複数銘柄全体の再現と説明しない。同じコードでも売買時刻や結果の一致までは保証しない。

MT4の制約は[公式テスター仕様](https://docs.mql4.com/runtime/testing)、排他アクセスは[ファイルのオープンフラグ](https://docs.mql4.com/constants/io_constants/fileflags)、一時共有変数は[GlobalVariableTemp](https://docs.mql4.com/globals/globalvariabletemp)の仕様に従う。

## 8. 実装時の確認と引継ぎ

新規EAでは本構成を使用する。既存EAの移行では、直接の注文API、再試行、終了時の注文取消、永続状態を追跡し、共通処理と二重管理にならないようにする。規約適用のためだけに対象外のEAを変更しない。

文字コード・改行・入力設定との互換性、共有部品の利用箇所、対象ソースのコンパイルなどは、MQL4リポジトリの `AGENTS.md` に従う。共通モジュール変更時は、影響する利用EAを特定する。

完了報告では、変更したEAと共通部品、残る未対応の注文経路、コンパイル結果、確認できた事項と未確認事項を明示する。規約の作成やコンパイル成功を、注文制御の実装完了・売買動作の確認・実運用への導入完了の代わりにしない。
